# Gram Wallet

Telegram Mini App — некастодиальный кошелёк для GRAM на контракте
[WalletTg](https://github.com/ton-blockchain/tg-wallet-contract).

**Приложение неофициальное и не связано с Telegram.** Это сторонний клиент
к открытому контракту.

---

## Главное про архитектуру

**Бэкенда нет вообще.** Toncenter и ton-access отдают CORS, поэтому браузер
обращается к блокчейну напрямую. Vercel раздаёт только статику.

Это не оптимизация, а требование: нет сервера — нет места, где могли бы
оказаться чужие ключи, нет логов и нет базы. Любая серверная функция сломала бы
главное обещание приложения.

**Seed-фраза живёт только в `localStorage`**, зашифрованная PIN-кодом.
Подробно — в разделе «Как устроена защита».

`Telegram.WebApp.CloudStorage` для seed-фразы **не используется никогда** — это
серверы Telegram.

## Контракт

Кошелёк работает на **WalletTg** — контракте кошелька от команды Telegram:

**https://github.com/ton-blockchain/tg-wallet-contract**

Контракт открытый и публичный, разворачивать его может кто угодно. Это
приложение — сторонний клиент к нему, а не часть Telegram и не продукт его
команды.

Что важно знать про сам контракт:

- **Ревизия 0.** Контракт новый, байткод может меняться голосованием
  валидаторов — логика живёт в сети, а не в самом кошельке, поэтому
  «переезжать» на новую версию, как было с v3 и v4, не нужно.
- **Ключ меняется, адрес — нет.** Адрес считается от *первого* публичного
  ключа и фиксируется навсегда. После ротации адрес из фразы уже не выводится,
  поэтому резервная копия обязана содержать фразу **и** адрес.
- **До 255 переводов за одну транзакцию** — сообщения кодируются змейкой
  чанков, реализация в `src/core/serialize.js`.
- **Другие кошельки его пока не поддерживают.** Фраза от WalletTg не откроется
  в Tonkeeper или кошельке Telegram, и наоборот — импорт чужих фраз здесь
  распознаётся и отклоняется с объяснением.

Байткод контракта зашит в `src/core/constants.js` как `TRAMPOLINE_BOC` —
41 байт, ровно тот же, что публикует репозиторий выше.

## Как устроена защита

Описано открыто и намеренно. Стойкость шифра не должна зависеть от того,
знает ли кто-то, как он устроен: если система ломается от публикации своего
устройства, она сломана и без публикации. Здесь нет ни ключей, ни данных
пользователей — только алгоритм, а он держится на секрете, который знает
один человек.

### Что и чем шифруется

Seed-фраза шифруется **AES-GCM-256**. Ключ выводится из PIN через
**Argon2id** (32 МБ памяти, 3 прохода, параллелизм 1). В `localStorage`
попадает только шифротекст вместе с солью, вектором инициализации и
параметрами вывода ключа — сам PIN не сохраняется нигде и никуда не
передаётся.

Соль и вектор берутся из `crypto.getRandomValues` при каждом сохранении,
поэтому два одинаковых PIN дают разный шифротекст.

Неверный PIN не проверяется отдельной сверкой: AES-GCM аутентифицирован,
и расшифровка с чужим ключом просто не проходит проверку тега.

### Почему Argon2id, а не PBKDF2

PIN короткий, и вся стойкость держится на том, сколько стоит **одна** попытка
перебора. PBKDF2 не требует памяти, поэтому видеокарта считает его тысячами
потоков параллельно. Argon2id на каждую попытку занимает 32 МБ — столько
памяти на тысячу ядер не выдать, и перебор замедляется на порядки.

Честная оценка для шести символов из букв и цифр без учёта регистра
(36⁶ ≈ 2,2 млрд вариантов), одна современная видеокарта:

| вывод ключа | перебор всего пространства |
| --- | --- |
| PBKDF2-SHA256, 600k итераций | около суток |
| Argon2id, 32 МБ, 3 прохода | порядка месяцев |

Это оценка порядка, а не гарантия. Вывод из неё простой и он не скрывается:
**PIN превращает утёкшую копию хранилища в задачу, которую надо решать, но не
делает её нерешаемой.** Настоящая защита seed-фразы — записанная на бумаге
фраза и то, что копия хранилища вообще никуда не утекает.

### Запасной путь

Argon2id живёт в WebAssembly. Если модуль не соберётся — старый webview,
жёсткая политика безопасности, — код не падает: он шифрует PBKDF2-SHA256
с 1,2 млн итераций и записывает выбранный способ прямо в запись, чтобы
расшифровать её потом тем же способом. Кошелёк работает в любом случае,
но защита в этом варианте слабее.

Записи первой версии (PBKDF2, 600k) читаются по-прежнему и молча
перешифровываются на Argon2id при первой удачной разблокировке.

### Почему в CSP есть `'wasm-unsafe-eval'`

Content Security Policy запрещает странице создавать исполняемый код на лету.
Сборка WebAssembly-модуля попадает под тот же запрет — без разрешения
Argon2id не собрался бы.

Разница между двумя ключевыми словами существенная:

- `'unsafe-eval'` разрешает превратить **любую строку** в исполняемый
  JavaScript. Это главный вектор XSS, и его здесь **нет**.
- `'wasm-unsafe-eval'` разрешает только собрать WebAssembly-модуль. Строку
  в код превратить нельзя.

`script-src` остаётся `'self'`: скрипты грузятся только со своего домена.
Сам модуль Argon2id вшит в бандл как base64 — за ним никуда не ходят,
и `connect-src` ради него не расширялся.

### Чего защита не делает

- Не спасает от того, кто смотрит через плечо, пока вводится PIN.
- Не спасает от вредоноса, который читает экран или память приложения.
- Не восстанавливает доступ: забытый PIN означает, что открыть хранилище
  нечем. Помогает только записанная seed-фраза.
- Не защищает адрес — он публичен по природе блокчейна и хранится открыто,
  чтобы экран блокировки мог показать, о каком кошельке речь.

## Запуск

```bash
npm install
npm run dev      # http://localhost:5173, доступен и по локальной сети
npm test         # офлайн-проверки, сеть не нужна
npm run build
```

## Деплой

1. `npm run build`
2. Vercel: импортировать папку, framework Vite. Заголовки безопасности и
   SPA-rewrites уже в `vercel.json`.
3. BotFather: `/newbot`, затем `/setmenubutton` с адресом приложения.

Кода бота нет и не нужно — кнопка запуска настраивается прямо в BotFather.

## Что проверяют тесты

`test/encoding.test.js` — кодирование `array<MessageToSend>` для пакетной
отправки против точной копии `parseArrayAndSend` из контракта: порядок
сообщений, границы чанков, `assertEnd`, отказ на пустом массиве и на 256
сообщениях.

`test/rotation.test.js` — форма запроса смены ключа: опкод, заголовок,
доказательство владения новым ключом и то, что оно **не** проходит проверку
чужим ключом.

Оба работают офлайн на случайных ключах.

## Грабли, заложенные в код

**Адрес нельзя выводить из ключа после смены ключа.** Адрес в TON — это хеш
начального stateInit с *первым* публичным ключом. После ротации он остаётся
прежним, но из нового ключа не вычисляется. Поэтому адрес хранится явно, а при
импорте есть отдельное поле для него.

**Публичные ноды врут.** Часть из них отдаёт живой аккаунт как `uninitialized`
с нулевым балансом. `getState()` принимает «не задеплоен» только после
подтверждения с нескольких нод — иначе приложение прицепило бы stateInit и
взяло seqno 0.

**ton-access залипает на одной ноде**, поэтому вторым провайдером идёт
toncenter напрямую: смена эндпоинта должна реально менять источник.

**External-запросы обязаны нести `IGNORE_ERRORS`**, иначе контракт откинет их
с ошибкой 137. Проверяется на клиенте до отправки.
